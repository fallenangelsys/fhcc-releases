# FHCC UI-Konsolidierung und 10/10-Visual-Qualität Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Die FHCC-App soll wie ein bewusst gestaltetes Gothic-Luxury-Control-Center wirken: eine visuelle Sprache, klare Hierarchie, belastbare Zustände und keine generischen oder zufällig unterschiedlichen Oberflächen.

**Architecture:** Eine autoritative Theme-Schicht liefert Tokens und primitive Komponenten. Bestehende Modul-CSS-Regeln werden schrittweise auf diese Primitives umgestellt; Inline- und Spezial-CSS darf nur noch für echte Embed-/Discord-Vorschauen oder isolierte Editor-Funktionen existieren. Verhalten, API-Verträge und Nutzerdaten bleiben unverändert.

**Tech Stack:** Electron 43, native Renderer-JavaScript, CSS, bestehende Smoke-Skripte, Playwright/Web-App-Tests sofern verfügbar.

## Global Constraints

- Kein Modul darf eigene globale Button-, Card-, Input- oder Status-Grundregeln einführen.
- Ein Zustand muss überall dieselbe Bedeutung und dieselbe visuelle Semantik haben: aktiv, deaktiviert, lädt, erfolgreich, Warnung, Fehler, offline.
- Keine rein dekorativen Glows, riesigen abgerundeten Karten oder Marketing-Hero-Flächen im Arbeitsbereich.
- Dunkle Gothic-Luxury-Richtung bleibt erhalten: Graphit/Obsidian, kontrolliertes Violett, kalte helle Akzente, dezente Linien und keine UI-Fläche mit Discord-Klon-Optik.
- Tastaturfokus, Kontrast, disabled/loading states und mobile Breiten werden für jede gemeinsame Komponente geprüft.

## Befund aus der Gesamtprüfung

- `desktop/renderer/index.html` lädt `ui-base.css`, `ui-aurora.css` und `ui-system.css` gleichzeitig; beide späteren Dateien definieren eigene Design-Token und überschreiben dieselben Alias-Namen.
- `desktop/renderer/ui-base.css` ist mit ca. 757 KB und 14.797 Zeilen zu groß für eine nachvollziehbare Basis und enthält historisch zusammengeführte Regeln.
- `desktop/renderer/ui-aurora.css` und `desktop/renderer/ui-system.css` beschreiben beide ein vollständiges Design-System, obwohl nur eines autoritativ sein darf.
- `desktop/renderer/setup.css` und `setup-polish.css` verwenden einen separaten Token-Satz; Setup wirkt dadurch wie eine andere Anwendung.
- `desktop/renderer/fh-source-bridge.js` injiziert eine zusätzliche helle/lila Oberfläche für öffentliche Seiten und Editor-Overlays; diese Regeln teilen keine gemeinsame visuelle Quelle.
- Viele Module definieren eigene Farben, Radien und Button-Regeln in JavaScript/CSS. Dadurch entstehen abweichende Aktiv-Buttons, Statuspunkte, Kartenhöhen und Abstände.
- `modern-ui-v5.js` und dynamische Renderer-Stile erhöhen die Kaskaden-Komplexität und erschweren visuelle Regressionstests.
- Die vier alten Dark-Angel-Preview-HTML-Dateien und die Command-Deck-Preview sind Referenz-/Experimentflächen, aber nicht als verbindlicher visueller Vertrag markiert.

## Phase 1: UI-Inventar und visuelle Verträge

- [ ] Komponenten-Inventar aus `index.html`, allen Renderer-Skripten und CSS-Dateien erstellen: Navigation, Sidebar, View-Header, Card, Formfeld, Select, Toggle, Button, Badge, Status, Toast, Modal, Empty State, Loading State, Preview.
- [ ] Gemeinsame Zustände und erlaubte Variants in `desktop/renderer/ui-contract.json` dokumentieren.
- [ ] `scripts/ui-style-audit.mjs` anlegen: doppelte Root-Tokens, globale Button-Regeln, Inline-Style-Injektionen, nicht definierte Zustandsklassen und harte Akzentfarben melden.
- [ ] Audit mit `npm run ui:style-audit` ausführbar machen und den Baseline-Bericht in `docs/ui-audit-baseline.json` ablegen.

## Phase 2: Eine autoritative Theme-Schicht

- [ ] Neue autoritative Datei `desktop/renderer/ui-theme.css` mit Obsidian/Gothic-Luxury-Tokens, Typografie, Spacing, Radien, Linien, Schatten, Statusfarben und Fokus-Ringen erstellen.
- [ ] `desktop/renderer/ui-primitives.css` für gemeinsame `.button`, `.field`, `.select`, `.toggle`, `.card`, `.badge`, `.status`, `.empty-state`, `.loading` und `.modal`-Primitives erstellen.
- [ ] `index.html` auf die definierte Reihenfolge umstellen: Basis/Theme/Primitives/komponentenbezogene Styles; keine konkurrierenden Vollsysteme mehr.
- [ ] `setup.css` und `setup-polish.css` auf dieselben Tokens umstellen, ohne den Setup-Flow funktional zu ändern.
- [ ] `ui-aurora.css` und `ui-system.css` zunächst als Kompatibilitätslayer markieren, anschließend Regelgruppen nach erfolgreicher Migration entfernen.

## Phase 3: Konsolidierung der Arbeitsoberfläche

- [ ] Navigation, Sidebar, View-Titel und Modulfilter in `desktop/renderer/ui-base.css`/Komponentenstyles auf die Primitives umstellen.
- [ ] Alle Statusbuttons reparieren: sichtbarer Unterschied zwischen aktiv, inaktiv, lädt, fehlerhaft und nicht verfügbar; Text und Farbe dürfen nicht die einzige Unterscheidung sein.
- [ ] Toggle-Komponente vereinheitlichen: 44px Mindesttrefferfläche, sichtbarer Thumb-Position, Fokus, disabled und aria-Status.
- [ ] Embed Studio, Modulkonfiguration, Diagnose, Serververwaltung, Activity League, Levels, Counting, TempVoice und Economy auf identische Feld-/Action-Layouts bringen.
- [ ] Wiederkehrende UI-Texte und Buttonbreiten so überarbeiten, dass lange deutsche Labels nicht umbrechen oder Controls verschieben.
- [ ] `fh-source-bridge.js` auf Theme-Variablen umstellen; helle öffentliche Seiten bleiben absichtlich separat, dürfen aber keine globalen App-Stile überschreiben.

## Phase 4: Visuelle Identität statt generischer Dashboard-Optik

- [ ] Dichte, asymmetrische Arbeitslayouts mit klarer Inhaltsachse und gezielten Akzentflächen definieren; keine überall identischen Kartenraster.
- [ ] FHCC-spezifische Details einsetzen: schmale Kapitelmarker, feine gravierte Linien, kontrollierte violette Lichtkante, klare Systemlabels und konsistente Fallen-Heaven-Bildsprache.
- [ ] Hero-/Welcome-Flächen auf funktionale Übersicht reduzieren; der erste Screen muss sofort Status, Server, aktive Module und nächste Aktion zeigen.
- [ ] Karten nur für echte Gruppen verwenden; verschachtelte Karten und dekorative Container entfernen.
- [ ] Responsive Layouts für 1440x900, 1280x720, 1024x768 und 390x844 festlegen.

## Phase 5: Visuelle Regression und Abnahme

- [ ] `scripts/ui-visual-contract-smoke.mjs` erstellen: alle Views laden, zentrale Komponenten finden, fehlende Zustandsklassen und horizontales Overflow melden.
- [ ] Playwright-Screenshots für Login, Übersicht, Module, Embed Studio, Diagnose, Setup und mindestens drei komplexe Modulpanels erzeugen.
- [ ] Pixel-/DOM-Prüfungen für Buttonzustände, sichtbaren Fokus, keine Überlappungen, keine abgeschnittenen Texte und mobile Scrollbarkeit hinzufügen.
- [ ] `npm run lint`, `npm run ui:field-audit`, `npm run ui:style-audit`, `npm run ui:visual-contract` und die bestehenden Smoke-/Release-Tests als UI-Gate bündeln.
- [ ] `PROJEKT-WISSEN.md` um Tokenquelle, Layer-Reihenfolge, Komponentenvertrag und bekannte Ausnahmen ergänzen.

## Definition of Done

- Genau eine autoritative Theme- und Primitive-Schicht für die native App.
- Keine widersprüchlichen globalen Button-/Card-/Toggle-Grundstile.
- Alle aktiven Zustände leuchten bzw. markieren sich eindeutig und sind auch ohne Farbe verständlich.
- Keine Überlappungen, abgeschnittenen Texte oder Layoutsprünge in den geprüften Desktop-/Mobile-Ansichten.
- Setup, Dashboard, Module und Studio wirken wie dieselbe Anwendung.
- UI-Audit und visuelle Regressionstests laufen reproduzierbar vor jedem Release.

## Self-Review

Der Plan behebt zuerst die Kaskaden- und Token-Ursache der Uneinheitlichkeit. Danach werden gemeinsame Primitives und Zustände migriert, bevor die visuelle Identität verfeinert wird. So wird kein einzelnes Panel hübsch gemacht, während der Rest der App weiterhin aus konkurrierenden Designsystemen besteht.
